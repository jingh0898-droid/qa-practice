# 接口自动化：Postman 集合与断言

集合文件：`03-api-tests/postman-collection.json`（共 16 个请求，分 2 个文件夹）

## 怎么用

1. 打开 Postman → 左上角 **Import** → 选 **File** → 选本目录下的 `postman-collection.json` → Import
2. 左侧会出现集合 **restful-booker 接口自动化（qa-practice）**
3. 点集合名旁的 **▶ Run**（或右上角 **Run collection**）→ 打开 Runner 面板 → 点 **Run**
4. 看报告：绿色 = 通过，红色 = 不通过；右上角显示 `xx% passed`

**不要手动一个个 Send。** Run 的意义是按顺序跑完整条链路：先拿 token → 再建订单 → 再改 → 再删，中间靠集合变量传值。

## 变量是怎么传的（这是自动化的关键）

集合里定义了两个空变量：

| 变量 | 谁写入 | 谁使用 |
|---|---|---|
| `{{token}}` | `02-获取 token` 的脚本自动写入 | `06`、`07`、`15`、`16` 的 Cookie 头 |
| `{{bookingId}}` | `03-创建订单` 的脚本自动写入 | `05`、`06`、`07`、`08` |

写入靠这一行：

```javascript
pm.collectionVariables.set("token", pm.response.json().token);
```

这样一来，token 和订单 id **不需要手抄**，也就不存在“抄错一位”“token 过期”这类问题——这正是接口自动化最先解决的那类痛点。

## 断言写什么（比脚本怎么写更重要）

每一条断言都要能回答「它错了会怎样」。本集合里的断言分四类：

| 断言类型 | 例子 | 防的是什么 |
|---|---|---|
| 状态码 | `pm.response.to.have.status(200)` | 接口是否按约定响应 |
| 字段存在 | `.to.have.property("token")` | 返回结构是否完整 |
| 类型正确 | `.to.be.a("number")` | `2` 与 `"2"` 混用导致的隐性 bug |
| 值正确 | `.to.eql(999)` | 更新是否真的生效（而不是回显旧值） |

**最容易漏的是「类型」和「值」**：只看状态码 200 就放过，等于没测。调用更新接口后必须断言字段值真的变了——这是 BUG-002 那类“返回成功但存了脏数据”问题唯一能被自动化抓住的地方。

## 为什么有 5 个用例是「预期失败」

`02 反向用例与鉴权` 文件夹里，`12`–`14`、`16` 故意断言不可能成立的期望值（如“非法日期应返回 400”），因为当前实现确实没做到。它们跑出来会红——**红不是脚本错了，是缺陷还在**。

这是自动化测试的正确用法之一：**把已知缺陷固化成失败用例**。缺陷修复后这行断言自然变绿，缺陷就算被回归验证过。因此：

- 报告里出现这 4 条红，属**正常**，对应 `02-bug-reports/BUG-002-订单创建缺少参数校验.md`
- 如果哪天它们变绿了，说明缺陷被修复，应更新 BUG-002 状态并提交回归记录

## 已知局限

- 依赖公共练习站，他人可能改动共享数据（曾出现自建订单被删、PUT 返回 405），因此每次 Run 都用「先创建再操作」的方式，不写死 id
- 该站存在短时高频拦截，脚本连续跑时偶发 403；遇到时先单独重跑该请求，不要立刻判定鉴权失败
- 本集合仅覆盖单接口与简单链路；跨接口业务链路、数据隔离、持续性回归（如每晚定时跑）属下一阶段内容
