# BUG-002 订单创建接口缺少参数校验，非法数据可写入并返回成功

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-002 |
| 缺陷标题 | POST /booking 未校验请求参数：非法类型与非法日期均返回 200 并入库，缺失字段返回 500 |
| 发现时间 | 2026-11-13 |
| 发现人 | jingh0898-droid |
| 所属模块 | 订单创建 / POST /booking |
| 严重程度 | 严重 |
| 优先级 | 高 |
| 复现频率 | 必现（多次执行均复现） |
| 测试环境 | Windows 11 / Postman 12.36.4 / 被测地址 https://restful-booker.herokuapp.com |
| 前置条件 | 已知接口文档，`POST /booking` 需提交完整订单对象 |

## 复现步骤

均以 `Content-Type: application/json`、`Accept: application/json` 提交以下 Body：

**场景一：`totalprice` 传字符串**
```json
{
  "firstname": "Jing", "lastname": "Hu",
  "totalprice": "abc", "depositpaid": true,
  "bookingdates": {"checkin": "2026-11-20", "checkout": "2026-11-22"},
  "additionalneeds": "x"
}
```

**场景二：`checkin` 传非法日期**
```json
{
  "firstname": "Jing", "lastname": "Hu",
  "totalprice": 120, "depositpaid": true,
  "bookingdates": {"checkin": "2026-13-45", "checkout": "2026-11-22"},
  "additionalneeds": "x"
}
```

**场景三：缺失 `firstname` 字段**、**场景四：Body 传 `{}`**、**场景五：缺失 `bookingdates` 字段**

## 实际结果

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 1. `totalprice` 为 `"abc"` | **200** | `{"bookingid":4562,"booking":{...,"totalprice":null,...}}` —— 非法值被存成 `null`，订单创建**成功** |
| 2. `checkin` 为 `2026-13-45` | **200** | `{"bookingid":4569,"booking":{...,"bookingdates":{"checkin":"0NaN-aN-aN","checkout":"2026-11-22"},...}}` —— 日期被存成 `0NaN-aN-aN`，订单创建**成功** |
| 3. 缺 `firstname` | **500** | `Internal Server Error` |
| 4. Body 为 `{}` | **500** | `Internal Server Error` |
| 5. 缺 `bookingdates` | **500** | `Internal Server Error` |

## 预期结果

服务端应在**入库前**完成参数校验，任何不合法输入都不得写入数据库，并返回语义明确的状态码：

1. 字段缺失（`firstname`、`lastname`、`totalprice`、`depositpaid`、`bookingdates` 任一缺失）→ **400 Bad Request**，响应体给出具体缺失字段名；
2. 类型错误（`totalprice` 非数字、`depositpaid` 非布尔）→ **400**，说明期望类型与实际类型；
3. 日期格式错误或不存在的日期（如 `2026-13-45`）→ **400**，说明要求的格式（`YYYY-MM-DD`）；
4. 任何情况下都不应返回 **500**：500 表示服务端异常，属于“程序崩了”，而不是“你的输入有问题”。

## 影响与理由

**这是数据质量问题，比接口报错严重得多。** 报错是“这次没成功”，用户重试即可；脏数据是“成功了但存错了”，问题会潜伏到下游才爆发：

- `totalprice: null` 入库后，所有涉及金额的计算（订单总额、结算、报表、对账）都会出现 `null` 参与运算，轻则展示为空，重则抛异常或按 0 计算导致少收款；
- `checkin: "0NaN-aN-aN"` 是日期解析失败后的产物（典型的前端/后端 JS `Date` 解析结果），任何按日期排序、筛选、统计入住率的逻辑都会失效，且这种字符串无法被正常解析回来；
- 缺字段返回 500 会把“用户输入错误”伪装成“系统故障”，掩盖真实原因，导致监控告警被误判为服务不可用。

此外，**入参校验缺失本身就是安全风险**：攻击者可提交超长字符串、特殊字符、脚本片段等，若下游未做转义，可能引发存储型 XSS 或注入问题。因此本缺陷评为「严重」。

## 修复建议

1. 在接口层引入统一的请求体校验（Schema 校验，如 JSON Schema / 参数校验框架），**校验失败统一返回 400 + 明确的字段级错误信息**；
2. 对 `totalprice` 强制数字类型并限定范围（如 ≥ 0），非数字直接拒绝，不要隐式转成 `null`；
3. 对 `bookingdates.checkin` / `checkout` 校验格式与真实存在性（`2026-13-45` 必须拒绝），并校验 `checkin < checkout`；
4. 增加全局异常处理：参数类异常返回 400，禁止把内部异常直接暴露为 500；
5. 补充接口自动化用例，将上述五个场景固定为回归用例，防止后续改动再次放开校验。
